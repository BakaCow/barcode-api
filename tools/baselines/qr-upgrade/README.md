# Baseline protocol for the QR update

Use the complete baseline commit `1821c9324b492af5f42024a1e7efb7345e7942ac`. Both sides must use the same current byte-aware scoring tools, with separate runtime roots. Never combine an old worker with current helpers or WASM.

From the current repository, with Node and the Python environment active:

```powershell
$qrBaselineRepository = Join-Path (Split-Path (Get-Location).Path -Parent) 'barcode-qr-baseline'
git worktree add --detach $qrBaselineRepository 1821c9324b492af5f42024a1e7efb7345e7942ac
if ($LASTEXITCODE -ne 0) { throw 'Could not create the baseline checkout.' }
New-Item -ItemType Directory -Force data/local | Out-Null

node tools/benchmark-accuracy.mjs --runtime-root $qrBaselineRepository --corpus tests/fixtures/damage-stress-qr-upgrade.json --output data/local/qr-browser-before.json
node tools/benchmark-accuracy.mjs --corpus tests/fixtures/damage-stress-qr-upgrade.json --output data/local/qr-browser-after.json
python tools/benchmark-damage-api.py --reader (Join-Path $qrBaselineRepository 'barcode_reader.py') --corpus tests/fixtures/damage-stress-qr-upgrade.json --output data/local/qr-api-before.json
python tools/benchmark-damage-api.py --corpus tests/fixtures/damage-stress-qr-upgrade.json --output data/local/qr-api-after.json

node tools/benchmark-accuracy.mjs --runtime-root $qrBaselineRepository --corpus tests/fixtures/qr-byte-safety.json --output data/local/qr-semantics-browser-before.json
node tools/benchmark-accuracy.mjs --corpus tests/fixtures/qr-byte-safety.json --output data/local/qr-semantics-browser-after.json
python tools/benchmark-damage-api.py --reader (Join-Path $qrBaselineRepository 'barcode_reader.py') --corpus tests/fixtures/qr-byte-safety.json --output data/local/qr-semantics-api-before.json
python tools/benchmark-damage-api.py --corpus tests/fixtures/qr-byte-safety.json --output data/local/qr-semantics-api-after.json
```

For each POS image profile add `--enhance-live --pos-formats ean13,upca,code128,qr` to the browser damage commands. For the live retry-zero profile also add `--mode live`. Those commands make one worker request per fixed image. They do not run camera acquisition, source-resolution selection, a complete retry cycle or confirmation across exposures. Burst/source-resolution simulations must be reported separately.

The damage corpus has 171 positive transformations of nine payload groups and 48 negatives; its payloads and group identifiers are disjoint from all eight prior accuracy/damage corpora. The targeted safety corpus has 40 QR images from ten payload groups, eight other-format images from four groups, six two-label images and eight unencoded negatives. It covers raw binary, controls, UTF-8 byte sequences, Latin-1 bytes and all four QR error-correction levels. It does not claim explicit ECI, GS1 QR or structured-append coverage. Raw bytes and format are authoritative; printable ASCII also requires exact text. Other displayed text is recorded without changing byte truth to fit a decoder.

The generators call no decoder and select no cases based on outcomes. Both fixtures were regenerated byte for byte before evaluation. One specification-driven safety-fixture revision replaced a leading-zero EAN-13 payload with a nonzero prefix: the former has physically equivalent UPC-A representation and ambiguous strict format/byte truth. The original baseline aggregate had already been observed (54/54 positives, 8/8 negatives for both runtimes); no per-case or updated-algorithm outputs had been inspected. This was not a response to a failing case. Both baseline safety profiles were rerun after the correction. [The revision record](fixture-revision.json) retains the original and final hashes and the reason. Existing development tests cover UPC aliases; the fresh fixture does not claim that coverage.

No updated algorithm may inspect the new per-case outcomes before the final implementation freeze. All previous fixture sets, including `independent-upgrade`, are now development evidence. After this evaluation is published, tuning against these new cases requires another fresh evaluation split.

Keep nonzero benchmark exits when unexpected values or runtime errors occur. A correct value plus a wrong extra fails. A zero exit permits unread positives and must not be reported as a perfect read rate. Record per-format gains, lost exact reads, unexpected readings, negative rejections, actual dependency versions and complete runtime hashes. Paired timing runs should be sequential on an otherwise quiet host; synthetic host timings do not measure Android/iPhone speed.
